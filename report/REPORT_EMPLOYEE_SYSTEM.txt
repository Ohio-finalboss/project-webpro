รายงานการเพิ่มระบบพนักงานร้านดอกไม้ใน flower2
วันที่จัดทำ: 6 ตุลาคม 2026

ขอบเขตงาน
- เพิ่มเฉพาะส่วนพนักงานจากโฟลเดอร์ flower-shop ได้แก่ หน้าหลักพนักงานจัดดอกไม้ หน้าหลักพนักงานเคาน์เตอร์ คิวคำสั่งซื้อ รายละเอียดคำสั่งซื้อ การอัปเดตสถานะ การยืนยันการชำระเงิน และใบเสร็จ
- ในขอบเขตตอนเพิ่มระบบพนักงานครั้งแรกยังไม่ได้ย้ายระบบหน้าร้าน/สั่งซื้อของลูกค้า; รายการย้ายส่วนลูกค้าเพิ่มเติมบันทึกไว้ในหัวข้อวันที่ 12 ตุลาคม 2026 ด้านล่าง
- ใช้ฐานข้อมูลที่มีอยู่จริง: db/flowershop1.db (ชื่อไฟล์ตามที่ผู้ใช้ยืนยัน)
- คีย์คำสั่งซื้อใช้คอลัมน์ order_ID ตามฐานข้อมูลและโค้ดเดิมใน flower2; URL ใช้พารามิเตอร์ orderId และช่องค้นหาสถานะเดิมยังใช้ order_id

ไฟล์ที่แก้ไขจากของเดิม

1) server.js
- เปลี่ยนการเปิดฐานข้อมูลจากโหมดอ่านอย่างเดียวเป็นอ่าน/เขียน เพราะพนักงานต้องบันทึกสถานะคำสั่งซื้อและผลการชำระเงิน
- ยังคงการค้นหาสถานะเดิมที่หน้า / และคงการค้นหา order_id แบบไม่สนตัวพิมพ์เล็ก/ใหญ่, การ trim ช่องว่าง, จำกัดความยาว 30 ตัวอักษร และข้อความกรณีไม่พบรายการ
- รวมหน้าแดชบอร์ดพนักงานไว้ที่ /?role=florist และ /?role=counter เพื่อไม่ชนกับหน้าตรวจสอบสถานะเดิมที่ / 
- เพิ่มเส้นทางพนักงานสำหรับคิวช่างดอกไม้, รายละเอียดออเดอร์, อัปเดตสถานะ, รายการเคาน์เตอร์ทั้งหมด, ติดตามออเดอร์, รายการรอชำระเงิน, ยืนยันรับชำระ, ใบเสร็จ และสร้าง QR สำหรับหน้าเช็คสถานะเดิม
- ใช้ SQL แบบ parameterized และตรวจสถานะก่อนอนุญาตให้ขยับไปสถานะถัดไป
- ปรับสถานะการทำงานให้เข้ากับค่าที่ flower2 ใช้อยู่: รอจัด -> กำลังจัดช่อ -> จัดเสร็จแล้ว; การจัดส่งต่อด้วย กำลังจัดส่ง -> เสร็จสิ้น; การรับที่ร้านเปลี่ยนจาก จัดเสร็จแล้ว -> เสร็จสิ้น
- ปรับการอ่านข้อมูลช่อให้เข้ากับสคีมาฐานข้อมูล flower2 ซึ่งไม่มี order_detail_ID, bouquet_quantity และ card_color ในตารางที่เกี่ยวข้อง โดยใช้ rowid เป็นลำดับแสดงผล, ใช้ order_details.quantity เป็นจำนวนช่อ และแสดงชื่อจาก bouquet_templates ได้
- รายการดอกไม้/วัสดุแสดงจาก bouquet_items เมื่อมีรายการกำหนดเอง และใช้ template_items เป็นค่าทดแทนสำหรับช่อจากเทมเพลต
- ใช้ข้อมูลการชำระเงินล่าสุดของแต่ละออเดอร์ในรายการและรายละเอียด

2) package.json และ package-lock.json
- เพิ่ม qrcode เวอร์ชัน ^1.5.4 เพื่อสร้างภาพ QR ในใบเสร็จ ซึ่งเปิดหน้าเดิม /?order_id=<เลขที่คำสั่งซื้อ>
- ติดตั้งแพ็กเกจสำเร็จแล้ว

ไฟล์หน้าจอและสไตล์ที่เพิ่มเข้ามาจากระบบพนักงาน
- views/home.ejs: แดชบอร์ดพนักงานและสรุปจำนวนออเดอร์
- views/orders.ejs: คิวออเดอร์ของพนักงานจัดดอกไม้
- views/order-detail.ejs: ข้อมูลลูกค้า รายการช่อ ข้อมูลชำระเงิน และปุ่มอัปเดตงาน
- views/counter-home.ejs: ตารางงานของพนักงานเคาน์เตอร์
- views/receipt.ejs: ใบเสร็จพร้อม QR
- views/not-found.ejs: หน้ากรณีไม่พบออเดอร์
- views/partials/order-status.ejs และ views/partials/fonts.ejs: ส่วนย่อยสำหรับป้ายสถานะและแบบอักษร
- public/styles.css, public/order-pages.css, public/table-pagination.js: สไตล์และการแบ่งหน้าตารางของระบบพนักงาน
- ลิงก์ที่เดิมพาไป /shop ถูกเปลี่ยนเป็นลิงก์ตรวจสอบสถานะเดิมที่ / เพราะไม่ได้ย้ายระบบร้านค้าลูกค้า

ไฟล์เดิมที่คงไว้
- เนื้อหาและหน้าตรวจสอบสถานะเดิมยังอยู่ โดยภายหลังได้เปลี่ยนชื่อไฟล์ view จาก views/index.ejs เป็น views/check-order-status.ejs ตามคำขอ; public/style.css ไม่ได้แก้ไข
- ไม่มีการแก้ไขหรือย้ายไฟล์ฐานข้อมูลในขั้นตอนนี้; ระบบพนักงานจะเขียนค่า payment/status ขณะมีการใช้งานจริงตามหน้าที่ของระบบ

หมายเหตุการทำงาน
- flower2 มีค่าเริ่มต้นสถานะ รอจัด จึงปรับค่าปุ่มและเงื่อนไขสถานะของพนักงานให้ตรงกับค่าดังกล่าว แทนค่าภาษาในฐานข้อมูลของ flower-shop
- ระหว่างจัดส่งใช้สถานะ กำลังจัดส่ง ซึ่งยังแสดงเป็นป้ายสถานะบนหน้าตรวจสอบเดิมได้ แต่หน้าตรวจสอบเดิมไม่มีขั้นตอนแยกสำหรับสถานะนี้; หน้าตรวจสอบเดิมไม่ได้ถูกแก้ตามขอบเขตที่กำหนด
- ระบบต้นฉบับแสดงหน้าแยกบทบาทด้วย query string ไม่ได้มีการตรวจสอบบัญชี/รหัสผ่านก่อนเข้าหน้าพนักงาน การย้ายครั้งนี้คงพฤติกรรมดังกล่าว
- ตอนตรวจพบว่าตาราง orders และ payments ใน db/flowershop1.db ยังไม่มีรายการ จึงยืนยันการทำงานกับรายการจริง/การเปลี่ยนข้อมูลจริงไม่ได้ในรอบนี้; ตรวจเฉพาะ syntax ของ server.js และ compile โครงสร้าง EJS แล้วผ่าน

บันทึกการเปลี่ยนแปลงเพิ่มเติม: เปลี่ยนชื่อ view หน้าเช็คสถานะ
วันที่: 12 ตุลาคม 2026

- เปลี่ยนชื่อไฟล์ views/index.ejs เป็น views/check-order-status.ejs โดยคงเนื้อหา HTML/EJS และหน้าตาเดิมทั้งหมด
- แก้ server.js ใน route GET / ให้เรียก res.render('check-order-status', view) แทน res.render('index', view) ทำให้ Express เชื่อมต่อไปยังชื่อ view ใหม่ในโฟลเดอร์ views
- แก้ README.md ในรายการโครงสร้างไฟล์ให้แสดงชื่อ views/check-order-status.ejs
- ไม่เปลี่ยน URL หน้าเช็คสถานะ, ชื่อ query order_id, คำสั่ง SQL, รูปแบบการค้นหา หรือการทำงานของระบบพนักงาน
- ตรวจค้น reference ในโค้ดแล้วไม่พบการเรียกใช้ชื่อ index.ejs ที่ต้องเปลี่ยนเพิ่มเติม

บันทึกการเปลี่ยนแปลงเพิ่มเติม: นำระบบจัดช่อ ตะกร้า และ checkout จาก files และ views_(pleng) เข้า flower2
วันที่: 12 ตุลาคม 2026

ขอบเขตที่นำเข้า
- นำหน้าจัดช่อแบบโต้ตอบและเส้นทางเพิ่ม/แก้ช่อจาก files มาใช้
- นำ flow ตะกร้า กรอกข้อมูล ตรวจสอบคำสั่งซื้อ สร้างออเดอร์ ชำระเงินจำลอง และหน้าสำเร็จจาก views_(pleng) มาใช้
- เชื่อมทุกส่วนเข้ากับ db/flowershop1.db และเซิร์ฟเวอร์เดิมของ flower2; ไม่เปิดเซิร์ฟเวอร์หรือฐานข้อมูลแยก

ไฟล์ที่เพิ่ม
- routes/shop-builder.js: คัดลอกจาก files/shop.js และเก็บการโหลดแคตตาล็อก/เทมเพลต ตรวจจำนวนดอกไม้และวัสดุ เพิ่มช่อ แก้ช่อ และบันทึกตะกร้า
- routes/order-flow.js: ปรับ views_(pleng)/index.js จาก standalone server ให้เป็น Express router ที่ใช้ database และ app เดิม
- views/shop.ejs: หน้าจัดช่อแบบโต้ตอบพร้อมภาพตัวอย่าง การเลือกเทมเพลต ดอกไม้ กระดาษ ของตกแต่ง การ์ด และจำนวนช่อ
- views/cart.ejs: แสดงตะกร้า แก้จำนวน ลบช่อ และสรุปราคา
- views/inform.ejs: รับชื่อ เบอร์โทร วิธีรับ วันเวลา ชื่อผู้รับ และที่อยู่จัดส่ง
- views/check.ejs: ตรวจข้อมูลลูกค้า รายการช่อ ค่าจัดส่ง และยอดก่อนยืนยัน
- views/payment.ejs: หน้าชำระเงินจำลองและปุ่มยืนยันชำระ

ไฟล์เดิมที่แก้
- server.js: เพิ่ม express-session, body parsers, เปิด SQLite foreign_keys, เพิ่มตัวช่วยแสดงราคา และติดตั้ง shop-builder/order-flow routers โดยใช้ db connection เดิม
- routes/shop-builder.js: เปลี่ยน cart_ID เป็น crypto.randomUUID() ตามรูปแบบที่ตกลง; เปลี่ยน bouquet_ID เป็น BQT-<วันที่ YYYYMMDD>-<สุ่มเลขฐาน 16 ตัวใหญ่ 8 ตัว> และตรวจ ID ซ้ำก่อนใช้
- routes/order-flow.js: สร้าง order_ID ด้วย ORD-<วันที่>-<สุ่ม 8 ตัว>, payment_ID ด้วย PAY-<วันที่>-<สุ่ม 8 ตัว>, cart_ID เป็น UUID และ receipt_number เป็น RCPT-<ปี>-<เลขลำดับ 6 หลัก>
- routes/order-flow.js: เชื่อม order/payment/รายละเอียดและลบ cart ใน SQLite transaction; เก็บยอดรวมใน payments.amount; ใช้สถานะเริ่มต้น รอจัด และ payment_status รอการชำระ เพื่อให้พนักงานเดิมเห็นออเดอร์หลังยืนยันชำระ
- routes/order-flow.js: เมื่อกดยืนยันการชำระจะอัปเดต payments.payment_status และ payment_date โดยไม่เขียนสถานะการชำระทับ order_status
- routes/order-flow.js: แปลงวิธีรับจากฟอร์มให้ตรงกับ staff workflow คือ จัดส่ง หรือ รับที่ร้าน และใช้ค่าดังกล่าวใน orders.fulfillment_type
- routes/order-flow.js: ใช้ข้อมูลใน session เก็บ cart_ID และ orderInfo; ลบการกำหนด cart_ID คงที่ C00001 ที่เคยอยู่ใน GET /cart เพื่อไม่ให้ผู้ใช้หลาย session ไปใช้ตะกร้าเดียวกัน
- views/payment.ejs: เปลี่ยนตำแหน่งรูป QR ที่ไม่มีไฟล์จริงเป็นข้อความแจ้งให้ติดต่อร้าน; ปุ่มยืนยันแบบจำลองยังทำงานผ่าน route เดิม
- package.json และ package-lock.json: เพิ่ม express-session สำหรับเก็บตะกร้าข้ามคำขอ HTTP; ติดตั้งสำเร็จแล้ว

เส้นทางที่เชื่อม
- /shop แสดงหน้าจัดช่อ; POST /cart/add เพิ่มช่อ; /bouquet/edit/:id และ POST /bouquet/update/:id แก้ช่อ
- /cart, /cart/update/:bouquetId, /cart/delete/:bouquetId ดูและแก้ตะกร้า
- /inform, /check, /check/confirm รับข้อมูล ตรวจสอบ และสร้างออเดอร์
- /payment/:id, /payment/confirm/:id, /order-success/:id ชำระจำลองและแสดงผลสำเร็จ
- หน้าเช็คสถานะยังใช้ / และพารามิเตอร์ order_id; หน้าแดชบอร์ดพนักงานยังใช้ /?role=florist และ /?role=counter

การปรับจากโค้ดต้นทางให้ตรงกับ flower2
- orders ใน flower2 ไม่มี delivery_fee และ total_amount จึงไม่เพิ่ม/แก้ schema; ยอดรวมรวมค่าจัดส่งแล้วเก็บใน payments.amount และหน้า checkout ยังคำนวณ/แสดงค่าจัดส่งตาม flow เดิม
- payments ใน flower2 บังคับ payment_ID, payment_date และ receipt_number เป็น NOT NULL จึงสร้าง payment row พร้อมออเดอร์สถานะรอชำระ และสร้างเลข receipt_number ตั้งแต่เริ่มรายการ
- คงชื่อคอลัมน์ order_ID ของฐานข้อมูลและ URL ของระบบพนักงาน; order ID ที่สร้างไม่เกินข้อจำกัดความยาว 30 ตัวอักษรของหน้าเช็คสถานะเดิม
- ไม่มีการแก้ไขข้อมูลในไฟล์ฐานข้อมูลหรือเพิ่มคอลัมน์
- รายละเอียดความสามารถที่ทำไม่ได้เหมือนต้นฉบับทุกประการและเหตุผลอยู่ใน error-report.txt

บันทึกการเปลี่ยนแปลงเพิ่มเติม: เชื่อมต่อฐานข้อมูลฉบับที่อัปเดต
วันที่: 12 ตุลาคม 2026

ไฟล์ฐานข้อมูลและการเชื่อมต่อ
- ตรวจพบฐานข้อมูลฉบับใหม่ที่ `db/flowershop1 (1).db`; ไฟล์ `db/flowershop1.db` ที่ server.js อ้างถึงก่อนหน้านี้ไม่มีอยู่แล้ว
- แก้ `server.js` ให้เปิด `db/flowershop1 (1).db` ด้วย better-sqlite3 และเปิด foreign key ตามเดิม
- แก้ `README.md` ให้แสดงชื่อฐานข้อมูลปัจจุบัน และนำตัวอย่าง order_ID ORD-0001 ถึง ORD-0005 ที่ไม่รับรองว่ามีอยู่ในฐานข้อมูลใหม่นี้ออก

ปรับโค้ดให้ตรงกับโครงสร้างฐานข้อมูลใหม่
- ตรวจ schema แบบอ่านอย่างเดียว: พบตาราง bouquet_items, bouquet_templates, bouquets, cart, cart_items, employees, items, order_details, orders, payments และ template_items
- ตาราง `bouquets` มี `service_fee REAL NOT NULL` จึงแก้ `routes/shop-builder.js` ให้บันทึกและแก้ไขช่อโดยระบุ service_fee ครบทุกครั้ง ปัจจุบันกำหนดเป็น 0 เพราะโค้ด/ข้อมูลต้นทางไม่มีอัตราค่าบริการต่อช่อให้ใช้อ้างอิง
- แก้ `routes/order-flow.js` ให้อ่าน service_fee มาคำนวณราคาในตะกร้า/หน้าตรวจสอบ และบันทึก `delivery_fee` กับ `total_amount` ลง `orders` ตอนสร้างคำสั่งซื้อให้ครบตามคอลัมน์ใหม่
- เปลี่ยนหน้าชำระเงินและหน้าสำเร็จให้อ่านยอดจาก `orders.total_amount` ซึ่งเป็นยอดรวมที่เก็บในคำสั่งซื้อ
- แก้ `server.js` ให้ส่ง `delivery_fee` และ `total_amount` ไปยังหน้ารายละเอียดพนักงาน และส่ง `service_fee` ไปยังหน้ารายละเอียดช่อกับใบเสร็จ

- ไม่ใส่โลโก้; คง QR ติดตามสถานะและปุ่มพิมพ์ไว้ พร้อมเพิ่มรูปแบบพิมพ์ให้ซ่อนแถบนำทาง

บันทึกการเพิ่มแถบนำทางหน้าลูกค้าและปุ่มย้อนกลับ
วันที่: 13 ตุลาคม 2026

ไฟล์ที่เพิ่ม
- `views/partials/customer-nav.ejs`: partial แถบนำทางที่ลิงก์ไปหน้าแรก (`/`), สั่งทำช่อ (`/shop`), ตรวจสอบสถานะ (`/check-order-status`) และตะกร้า (`/cart`); ระบุหน้าปัจจุบันด้วย `aria-current` เพื่อการเข้าถึง
- `public/customer-nav.css`: รูปแบบแถบนำทางตามตัวอย่าง พื้นครีม ปุ่ม Home สีชมพู ปุ่มสั่งช่อสีเทา ปุ่มตรวจสอบสถานะแบบเส้นขอบ และปุ่มตะกร้าสีเขียวมะกอก พร้อมรูปแบบ responsive สำหรับจอแคบ

ไฟล์ที่แก้ไข
- `views/inform.ejs`: เพิ่มแถบนำทางโดยเลือกสถานะเมนูสั่งช่อ; คงลิงก์ย้อนกลับที่มีอยู่และปรับข้อความเป็น “ย้อนกลับไปตะกร้าสินค้า” โดยลิงก์กลับ `/cart`
- `views/check-order-status.ejs`: เพิ่มแถบนำทางโดยเลือกสถานะเมนูตรวจสอบสถานะ; คงฟอร์มค้นหาและการแสดงข้อมูลสถานะคำสั่งซื้อเดิม
- `views/shop.ejs`: เพิ่มปุ่ม Home รูปแบบเดียวกับ `customer-nav` ไว้ก่อนหัวข้อ “สั่งทำช่อดอกไม้”; คงลิงก์ตรวจสอบสถานะ ตะกร้า และรูปแบบการเลือกช่อเดิม พร้อมปรับตำแหน่งปุ่มให้พอดีกับหน้าจอขนาดเล็ก

การตรวจสอบ
- แถบนำทางใช้ลิงก์ที่มี route อยู่แล้วในระบบ และไม่เปลี่ยน route หรือการทำงานของฟอร์มติดต่อ/ฟอร์มตรวจสอบสถานะ

บันทึกการเพิ่มระบบอัปเดตข้อมูลแบบ SSE (Server-Sent Events)
วันที่: 13 ตุลาคม 2026

วัตถุประสงค์และการทำงาน
- เพิ่มการแจ้งเหตุการณ์จากเซิร์ฟเวอร์ไปยังหน้าเว็บด้วย SSE ที่ endpoint `GET /events` โดยใช้การเชื่อมต่อ HTTP แบบทางเดียวจากเซิร์ฟเวอร์ไปยังเบราว์เซอร์
- เมื่อมีการเปลี่ยนข้อมูลคำสั่งซื้อหรือการชำระเงินผ่านระบบ เซิร์ฟเวอร์จะส่ง event ชื่อ `shop-update` ไปยังหน้าเว็บที่เปิดเชื่อมต่ออยู่
- event ส่งเพียงสัญญาณว่าสถานะข้อมูลมีการเปลี่ยน ไม่ส่งชื่อ เบอร์โทรศัพท์ ที่อยู่ ยอดชำระ หรือข้อมูลลูกค้าไปใน stream
- หน้าเว็บที่รับ event จะเรียกหน้า GET ปัจจุบันแบบเบื้องหลัง แล้วแทนที่เฉพาะ element ที่ระบุ `data-live-region` โดยไม่รีโหลดทั้งหน้า
- หากข้อมูลใหม่ทำให้ route เปลี่ยน เช่น หน้าชำระเงินถูกเปลี่ยนเป็นหน้าแจ้งชำระสำเร็จ หน้าเว็บจะเปลี่ยนไปยัง URL ที่เซิร์ฟเวอร์ตอบกลับ
- SSE ตั้งค่าการเชื่อมต่อใหม่อัตโนมัติทุก 5 วินาทีเมื่อหลุด และส่ง heartbeat ทุก 25 วินาทีเพื่อคงการเชื่อมต่อและล้าง client เมื่อปิดหน้า
- เมื่อเชื่อมต่อกลับหลังหลุด หน้าเว็บจะดึงข้อมูลปัจจุบันอีกครั้งเพื่อชดเชย event ที่อาจเกิดขึ้นระหว่างขาดการเชื่อมต่อ

เหตุการณ์ที่ทำให้ระบบส่งอัปเดต
- ลูกค้ายืนยันคำสั่งซื้อใหม่: แจ้งให้แดชบอร์ดและรายการคำสั่งซื้อพนักงานเห็นออเดอร์ใหม่
- ลูกค้าแจ้งชำระเงิน: อัปเดตสถานะในหน้าความสำเร็จ หน้าตรวจสอบสถานะ และหน้ารายการรอตรวจสอบของพนักงานเคาน์เตอร์
- ลูกค้ายกเลิกออเดอร์ที่ยังรอชำระ: อัปเดตสถานะคำสั่งซื้อ/ชำระเงินในหน้าตรวจสอบสถานะและรายการพนักงาน
- พนักงานจัดดอกไม้เริ่มจัดหรือทำรายการจัดเสร็จ: อัปเดตคิว สรุปจำนวน และรายละเอียดออเดอร์ที่เปิดอยู่
- พนักงานเคาน์เตอร์ยืนยันการชำระเงิน: อัปเดตจำนวนรายการใบเสร็จ รายการที่รอตรวจ และหน้าความสำเร็จของลูกค้า
- พนักงานเคาน์เตอร์อัปเดตการส่งมอบหรือรับสินค้าสำเร็จ: อัปเดตตารางติดตาม แดชบอร์ด และหน้าตรวจสอบสถานะ

หน้าที่เชื่อมกับ SSE
- ฝั่งพนักงาน: แดชบอร์ดพนักงานจัดดอกไม้/เคาน์เตอร์, ตารางคำสั่งซื้อทั้งหมด, ตารางอัปเดตสถานะของพนักงานจัดดอกไม้, ตารางติดตาม/รอตรวจชำระของเคาน์เตอร์ และหน้ารายละเอียดออเดอร์
- ฝั่งลูกค้า: หน้าตรวจสอบสถานะคำสั่งซื้อ, หน้าชำระเงิน และหน้า `/order-success/:order_id`
- ตารางที่ถูกแทนที่หลัง event จะเรียกเตรียมระบบแบ่งหน้าใหม่ ส่วนการเปิดรายละเอียดจากแถวตารางใช้ event delegation จึงทำงานต่อได้หลังอัปเดต

ไฟล์ที่เพิ่ม
- `lib/sse.js`: สร้าง SSE hub, เก็บการเชื่อมต่อที่เปิดอยู่, กระจาย event แบบไม่มีข้อมูลส่วนตัว, ส่ง heartbeat และนำการเชื่อมต่อที่ปิดแล้วออกจากรายการ
- `public/live-updates.js`: เปิด EventSource, ดึงหน้าเดิมเมื่อได้รับ event, แทนที่ live region และรองรับกรณีที่การตอบกลับเปลี่ยน route

ไฟล์ที่แก้ไข
- `server.js`: สร้าง SSE hub, เปิด `GET /events` และส่ง event หลังการเปลี่ยนสถานะจากฝั่งพนักงานจัดดอกไม้/เคาน์เตอร์สำเร็จ
- `routes/order-flow.js`: รับ callback สำหรับส่ง event และแจ้งหลังสร้างออเดอร์ แจ้งชำระเงิน หรือยกเลิกออเดอร์สำเร็จ
- `public/table-pagination.js`: รองรับการสร้าง pagination ใหม่หลัง live region ของตารางถูกแทนที่ และป้องกันการสร้าง pagination ซ้ำให้ตารางเดิม
- `views/home.ejs`: เชื่อมสรุปและตารางล่าสุดของแดชบอร์ดพนักงานกับ live region และเปลี่ยนตัวเปิดแถวเป็น event delegation
- `views/orders.ejs`: เชื่อมตารางออเดอร์และคิวอัปเดตสถานะของพนักงานจัดดอกไม้ พร้อม event delegation สำหรับเปิดรายละเอียด
- `views/counter-home.ejs`: เชื่อมตารางคำสั่งซื้อ ติดตาม และรายการแจ้งชำระเงินของพนักงานเคาน์เตอร์
- `views/order-detail.ejs`: เชื่อมรายละเอียดและปุ่ม/สถานะของออเดอร์ที่เปิดอยู่
- `views/check-order-status.ejs`: เชื่อมผลการตรวจสอบสถานะออเดอร์ของลูกค้า
- `views/payment.ejs`: เชื่อมหน้าชำระเงิน เพื่อพาไปหน้าสถานะปัจจุบันได้เมื่อมีการเปลี่ยนข้อมูลจากอีกหน้าหนึ่ง
- `views/order-success.ejs`: เชื่อมหน้าความสำเร็จ เพื่อแสดงผลหลังพนักงานยืนยันการชำระเงินโดยไม่ต้องกดรีเฟรช

ผลต่อฐานข้อมูลและขอบเขต
- ไม่เปลี่ยน schema หรือข้อมูลในฐานข้อมูล; event จะถูกส่งหลังคำสั่งเขียนข้อมูลที่เกี่ยวข้องสำเร็จแล้วเท่านั้น
- การอัปเดตครอบคลุมการเปลี่ยนแปลงที่ทำผ่าน route ของแอปนี้ หากแก้ฐานข้อมูลจากเครื่องมือภายนอกโดยตรงจะไม่มี event ถูกส่ง
- ระบบยังใช้การเชื่อมต่อในหน่วยความจำของ process เดียว หากเปิดหลาย process/หลายเครื่อง ต้องเพิ่มตัวกลางกระจาย event เช่น Redis Pub/Sub เพื่อให้ทุก process แจ้งถึงกัน
- SSE เป็นช่องทางอัปเดตหน้าเว็บ ไม่แทนที่การตรวจสิทธิ์หรือ validation ของ route ที่เขียนข้อมูล

การตรวจสอบ
- ตรวจจุดเขียนสถานะคำสั่งซื้อ/ชำระเงินและจุด render หน้าพนักงาน/ลูกค้าเพื่อเชื่อม event กับหน้าที่เกี่ยวข้อง
- ไม่ได้รันทดสอบหรือเปิด flow สั่งซื้อจริงในการเปลี่ยนแปลงครั้งนี้
